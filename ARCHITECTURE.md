# Архитектура версии 3 Автогонки

Все четыре реализации используют одну модель и последовательную передачу ходов.
Различаются создание участников, семафоры и способ передачи данных. Судья управляет
раундами, экраном, журналом и ресурсами; процесс машины выбирает маршрут
и выполняет переходы своей машины.

## Модули

| Файл | Назначение |
|---|---|
| main.c | Общий вход судьи: параметры, сигналы, старт, раунды, итоги |
| car_main.c | Вход независимо запускаемой машины |
| race.c и race.h | Расстановка, маршруты, круги, сход, финиш и классификация |
| processes.c и processes.h | Общая память, семафоры, события, регистрация и завершение |
| queues.c и queues.h | Независимые процессы, POSIX-очереди и именованные семафоры |
| display.c и display.h | Текст, журнал, поклеточные кадры, паузы и восстановление терминала |
| tests/ | Независимые проверки правил, кадров, процессов и отказов |

Makefile собирает race с неименованными семафорами, race-named с именованными,
race-judge и race-car для независимого запуска с общей памятью,
race-mq-judge и race-mq-car для обмена очередями. Четыре судьи собираются
из одного main.c с фиксированным режимом. Правила находятся в race.c;
циклы обмена для памяти и очередей находятся в соответствующих модулях.

## Роли и общая память

При T командах по C машин работают N = T × C участников и судья.
По умолчанию всего 7 процессов, максимум — 33. В первых двух вариантах
судья создаёт детей через fork; в третьем и четвёртом машины запускаются отдельными
командами и не являются его детьми. Команда и трасса не имеют собственного
активного поведения и отдельного процесса.

SharedRace содержит Race, семафоры первого варианта, бюджет и стоимость,
текстовый буфер, данные кадра и атомарные поля регистрации/остановки.
PID, pidfd, адреса отображений, указатели sem_open и учёт ресурсов находятся
в локальном RaceProcesses. В общую память локальные адреса не записываются;
поле Race.config.log_path обнуляется. Для кадра передаётся индекс Car,
а не указатель, поскольку адрес отображения у независимых процессов разный.

Судья выполняет жеребьёвку с заданным seed. Генератор каждой машины
инициализирован seed + id с арифметикой unsigned int. Поэтому порядок
подключения и планирование ОС не меняют выбор маршрутов в одном окружении.
Последовательность random отличается от версии 2, где генератор был общим.

## Семафоры и передача хода

Для N машин используются N + 2 семафора с начальным значением 0:
permission[i], ready и consumed. В первом варианте sem_init с pshared=1
создаёт их в MAP_SHARED. Во втором и третьем sem_open создаёт или открывает
именованные POSIX-семафоры. Имена содержат сессию, поколение и номер объекта.

1. Судья фиксирует очередь раунда, записывает бюджет и публикует permission.
2. Машина выбирает маршрут и выполняет переходы. Текст и кадры публикуются
   как события TEXT и FRAME через ready.
3. До consumed машина ждёт. Судья читает стабильные данные, пишет текст
   или рисует кадр, затем подтверждает чтение.
4. В конце хода машина записывает фактическую стоимость и публикует DONE.
   Следующего подтверждения для DONE нет: машина ждёт новое permission.
5. Судья вычисляет следующий бюджет. После всей очереди выполняет отложенное
   снятие и пересчитывает порядок.

Выдано не больше одного игрового задания. Право изменять Race передаётся
семафорами, поэтому дополнительный mutex не нужен. Во время FRAME машина
не меняет модель до подтверждения: судья может отобразить клетки прямо из
общей памяти без копирования всей трассы для каждого кадра.

## Независимое подключение

race-judge создаёт объект /akos-session-NAME с правами 0600 и O_EXCL.
После инициализации данных и семафоров атомарно публикует состояние JOINING.
race-car ожидает существующий объект, проверяет размер и готовность,
открывает семафоры, находит индекс по ID и занимает регистрационный слот
через atomic_compare_exchange. Повторный ID отклоняется.

Каждая зарегистрированная машина один раз публикует ready и ждёт permission.
Судья получает N подтверждений регистрации; только после них тот же ready
используется для игровых событий. Дополнительные регистрации после перехода
в RUNNING запрещены. Ожидание состава ограничено --wait и отменяется сигналом. При остановке
свободные регистрационные слоты атомарно замораживаются, поэтому позднее
подключение не создаёт участника после начала очистки.

Для наблюдения за независимыми участниками судья открывает Linux pidfd.
Они позволяют заметить выход, включая состояние зомби, и отправить сигнал
уже привязанному процессу без обращения к повторно использованному PID.
Коды завершения независимых машин собирает их настоящий родитель, а судья
через poll ожидает окончания процессов.

## Время жизни ресурсов

В вариантах с fork после открытия объектов имена памяти и именованных
семафоров сразу удаляются: дети наследуют отображение и открытые семафоры.
В независимой версии имя памяти сохраняется до конца гонки, чтобы второй
судья с тем же NAME не создал конкурирующую сессию. Имена семафоров удаляются
после регистрации всех машин, когда все участники уже открыли их.

Учёт created, initialized, linked и owns_name различает созданные ресурсы
и чужие объекты. Отказ на любом шаге вызывает откат только своих ресурсов.
Закрытие семафоров и munmap выполняются после окончания участников;
ошибка одного освобождения не прерывает остальные попытки.

Если независимый судья аварийно погибает, машины замечают это через pidfd.
Одна машина атомарно получает право удалить оставшиеся имена. Перед удалением
проверяется inode объекта памяти; имена семафоров содержат поколение.
Старая машина поэтому не удаляет новую гонку с повторно использованным NAME.

## Обмен через очереди сообщений

Четвёртая реализация не отображает общую память. Судья владеет локальной
моделью Race, машина получает её копию в задании TURN. После каждого кадра
и в конце хода машина возвращает обновлённую копию. Адрес файла журнала
в сообщении обнулён. Игра, выбор маршрута и отображение используют общие функции.

Судья создаёт очередь /akos-mq-NAME-events и именованные семафоры ready,
ack и cleanup. Каждая машина создаёт очередь /akos-client-PID и одноимённый
семафор permission, затем посылает HELLO с ID и PID. Судья проверяет ID,
занятость места и жизнеспособность процесса. ACCEPT передаёт индекс машины,
начальную модель и параметры вывода. REJECT отклоняет подключение.

В очереди машины хранится одно задание; в общей очереди — до четырёх событий.
Размеры сообщений проверяются при компиляции на предел 8192 байт.
mq_send предшествует sem_post, поэтому разрешение всегда относится к уже
записанному сообщению. После TEXT и FRAME машина ждёт ack; после DONE ждёт
следующее permission. Игровое задание одновременно выполняет одна машина.
ready, ack и permission обеспечивают порядок, а данные находятся в очередях.

После подключения судья удаляет имена очереди и семафора машины: открытых
дескрипторов достаточно для работы. Имена судьи остаются до окончания сессии.
При ошибке частичного запуска удаляются только созданные данным процессом
объекты. Если судья погибает, одна из машин получает семафор cleanup,
проверяет inode очереди и удаляет оставшиеся имена сессии.

Ожидание и контроль pidfd устроены так же, как в независимой версии с памятью.
Сигнал машине передаётся судье через pidfd_send_signal из обычного кода,
после чего судья заканчивает текущий раунд. При штатном завершении участники
получают STOP; при аварии судья прекращает работу всех зарегистрированных машин.

## Сигналы и ошибки

У fork-детей SIGINT/SIGTERM заблокированы: сигнал всей группе обрабатывает
судья. Независимая машина принимает сигналы и передаёт запрос через атомарное
requested_signal. Судья проверяет его при ожидании и каждые 20 мс во время
паузы. Начатый раунд завершается целиком, новый не начинается.

sem_timedwait ожидает блокирующим образом с интервалом проверки 100 мс.
Судья проверяет детей через waitpid, независимых участников — через pidfd.
Если во время игрового обмена три секунды нет нового события, выполнение
прерывается с ошибкой. Время показа кадров в этот срок не входит.

При штатной остановке судья публикует STOPPING и будит участников.
При ошибке останавливает их принудительно. Ожидание штатного выхода ограничено
примерно секундой; зависший участник получает SIGKILL. Для fork выполняется
waitpid, для независимых процессов — ожидание pidfd, затем освобождение.
Незавершённый ход после аварии не выводится как итоговая классификация.

Независимые машины не принимают файл журнала и не рисуют экран. Все их
вызовы output и animate_frame перенаправлены судье. Унаследованный FILE
у fork-детей закрывается без повторного сброса буферов.
